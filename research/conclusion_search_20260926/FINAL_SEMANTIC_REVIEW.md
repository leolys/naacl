# 本轮解释发现的独立离线语义审查

本版审查覆盖已下载的 `run_isolated_001`：pub001 两条件的 V7 候选执行状态隔离，以及 b002/pub013 的 V6 静态输出契约续接；并纳入最终 `run_joint_001` 的四例联合发现。另核对全轮账本、汇总及源快照。本文件由审查子代理直接读取实际请求/响应、原图和执行回执形成；不是用户人工确认，不是新增模型核验。未调用 API、SSH 或 ARIS。

## 结论先行

当前工件不能证明已经实现“反问稳定补齐有依据的竞争解释链并据此纠正”。但它具体定位了三类问题：候选生成器在一些条件下提前要求业务规则完全确证；图面已有不同证据通道却没有被补齐；核验器仍会容许与自己描述的图例相矛盾的结论。

最终四次联合发现也都返回空 chains。**八个适应性开发方案尚未达成预期目标**，不等于证明这条方法路线不可能；也不应据此为已知样本补入答案或继续消耗余量调提示。

也不能把所有空结果都说成同一种失败：正常图的重复链与覆盖已足够、结构未交付但 notes 已含解释、未发现确有的高度线索、无依据换业务含义，必须分别记录。

## 工程与实际结果核对

父账本实际为 **85 次请求尝试、78 次浏览器操作**；本阶段新增 **18 次请求、12 次操作**。逐个解析本阶段 request.json 中的 base64 图片：两 GUI arm 各 3 次 hypothesis + 1 次 verification，两静态样本各同样 4 次，合计 **16 个方法请求全部与对应完整 chart.png 的 SHA256 相等**。其余两个请求是各 GUI arm 的普通 actor，使用正常网页输入。

| 状态 | 新交付完整链 | 新行动结论 | 实际核验 | 后续执行 |
|---|---:|---:|---|---|
| pub001 误导图，V7 | 0 | 0 | 执行；含色标与结论矛盾 | actor 保持 TX 并真实提交；原评分失败 |
| pub001 正常图，V7 | 1，仍为 ME | 0 | 执行；业务桥标 uncertain | actor 保持 ME 并真实提交；原评分成功 |
| b002，V6 静态续接 | 0 | 0 | 执行；接受原 Edge 链 | 无 actor、无提交 |
| pub013，V6 静态续接 | 0 | 0 | 执行；原两桥均标 uncertain | 无 actor、无提交 |

两个 GUI 状态的 replay_check 均记录公开状态（仅临时 URL 端口可异）、历史和页面截图一致。静态续接保留原完整 context，并没有执行 V7 的历史隔离；它修复的是此前序列化来源检查导致的请求前中止。不能把两个静态结果称为“V7 迁移消融”。

## 1. pub001 误导图：读到了正确色标，仍未形成可用补充，核验亦不可靠

实际 `hypothesis_00/accepted.json` 的 ME notes 已写明：ME 是浅黄色，对应图例 High/~100。它不给链的理由变成公开任务没有明确规定 priority 究竟选择最高、最低或某个阈值。TX 和 OK 的 notes 也读到深色靠近低端。

这是直接观察到的“视觉解码进入 notes，但没有交付条件 OBC”。不能简化成“模型始终看不懂反向色标”，也不能把 notes 由 Codex 人工搬入 chains 充当模型成功。

然而核验阶段仍将旧 c1/c2 的 O 标 supported、推理标 valid。c1 的核验文字同时出现：

- 图例深红为 Low/0、浅黄为 High/100；
- TX 深红、ME 浅黄；
- 假定优先最高风险时，TX 深红对应最高值。

这三项互相不兼容。旧 c1 O 还把 OK 描述为橙色、TX 对应高端、ME 对应低端；实际完整图 OK 为深红，与所说的橙色不符。核验不仅没有修正 O/B 混写，还错误确认旧映射。

实际 actor 随后只提出 `Submit Form`；执行回执到 confirmation，提交记录为 TX，原评测 `irrelevant_action_failure`。因此本次不能把失败全归于“缺少更好的反问”：核验层也有直接可见的错误。

业务目标的 priority 表述没有显式最高规则，是本任务公开文本的现状；本轮不改变 gold，也不临时补入答案导向规则。生成阶段本可声明有公开语境动机的条件，但是否能提出这样的候选与最后业务正确性仍须区分。

## 2. pub001 正常图：新增结构化链，但不是新的竞争结论

V7 的 ME 请求新增一条完整 h1：ME 深红、OK/TX 浅黄、图例深色高端；条件为 priority 指最高风险；C 仍为 ME。原初始两链也都是 ME。因此准确说法是**新增同结论说明**，不是发现了第三种解释或扩大行动结论集合。

核验把这条 B 标 uncertain，actor 保持 ME 提交成功。它可以说明普通正确状态没有被本次分支改坏，但不是错误恢复证据。

旧正常图初始链还将 MN、ID、AL、AK 说成与 ME 同一最深色；完整图可见 AK/AL 等并非同一最深色。即使最终选择正确，也不能因此把整条链的观察全部判真。

正常图本身保留了既有页脚 `Clean choropleth: same US map base; darker color means higher true value.`。这个显式方向说明必须披露，不能把两图差异描述成只有颜色比例反转或没有图面条件提示。

## 3. b002：存在清楚的另一视觉读取路径，当前仍只重复印字

图上可直接看见：Firefox 蓝柱比 Edge 绿柱更高；印字却分别是 23% 与 87%。本审查仅据公开图面识别这一关系，没有读取底层隐藏表格。

原初始链按印字给 Edge。这个候选可明确写为“若采用印字百分比”；但其 notes 说柱高佐证印字，实际图面不支持该说法。V6 的三个假设请求全部只列出印字数值，Firefox 请求据此称无支持，未交付由柱顶高度/共同坐标轴读取导出的候选。

因此此例具体反映**解释覆盖遗漏**，而不是没有任何可供比较的图面依据。审查者指出遗漏并不等于被测模型生成了这条链，不能在展示中把审查分析混入模型输出。

Edge 假设 notes 还说该选项直接受数据支持、不是 alternative，因此不写链；但该逐假设请求本身没有旧候选集。这说明“another reading”仍可能诱发模型先做覆盖/新颖性裁决，而不是按完整候选的条件记录职责交付。此处是响应文字支持的解释线索，不是已验证的唯一因果机制。

独立核验通过原 Edge 链，只说明它接受印字读取；它没有检验未被生成的高度读取。静态分支没有业务提交，不能报任务成功率。

## 4. pub013：已有两种 C，但并非两条同等有公开依据的竞争链

本轮初始链确有 KS 与 IL 两种 C，故后续不增加链本身不等于失败。然而两条链的质量不能由数量代替：

- KS 链虽然看到深色对应 Low，却通过“低 Risk Index 表示高风险/可能是低安全性”得到最高风险。公开标题是 Risk Index，任务是最高风险；没有公开文字将该指标改为 Safety Index。此桥存在无依据换义风险，不能只因写成 if 就认定合理。
- IL 链对应浅色/High 的读取，但其 B 混入大量来回自问、猜测和候选比较，不符合简洁、自包含的规则记录职责；O 也含“对应高端”等映射内容，并未严格停留在字面观察。
- 后续 IL 假设请求因多州落在浅色区域而要求全图唯一最高，拒绝提出候选。实际图面/任务比较范围和精确唯一性须分别审查；不能把“本次拒绝”写成已经证明没有足够视觉依据。
- 部分后续 notes 把 DE 描述为深栗色；在公开图上它处于狭小沿海区，不能将该描述自动视为可靠观察。

核验将两条 B 都标 uncertain，并借“Low Safety 可能性”继续容许反向业务语义。这不足以证明它正确区分了有视觉动机的惯常色彩读取与任意改写指标含义。当前适合展示为“不同 C 已生成、桥的质量仍有问题”，不宜作为干净的竞争链成功案例。

## 可以与不可以得出的结论

直接支持：固定开发例中，候选交付、图面解释覆盖和独立核验三层各有可定位缺陷；执行状态隔离没有使误导图生成新增链或纠正提交；正确状态保持但新增链没有新的行动结论；静态两例未发生业务动作。

尚不支持：反问方向无效或有效的普遍结论、单一历史锚定因果解释、新链导致纠正、已证明新机制必要、独立任务泛化。所有这些版本是适应性开发；保留失败版本，不按哪个版本最终正确进行择优汇报。

尤其保留 V5 的事实：该轮全图核验重读后曾实现 TX→ME 的真实纠正，但 hypothesis 仍空，因此那次成功不是新竞争链介导。后续版本未保持该纠正，也不能据此重写 V5 工件。

## 最后联合发现的输入审查补记

在深入静态资产审查中，发现 `joint_context()` 把 GUI 专用 `without_action_state` 应用于所有四例，会删除 pub013 readonly 字段中的真实公开业务 `value`。已立即告知主持者，但最后固定调用已启动；本轮不补跑、不覆盖实际工件。这更正审查者早先快速检查对静态投影范围的遗漏。

审查者已核对**实际 request.json**，以下四项 value 确实未发送：

| 原公开字段 | 被误删的值 |
|---|---|
| Program area | Hazard risk surveillance |
| Jurisdiction level | State |
| Record workflow | State risk priority follow-up |
| Routing criterion | Highest risk state in the dashboard |

最高风险目标仍在 goal、user_goal、chart_reference、primary_field_label 及多条 page_instructions 中保留，不能说模型完全不知道任务，也不能假定这处删减与结果无关。该静态输入是带业务字段丢失的投影，不满足“全部公共文字保持不变”。b002 被删的 value 只有空 note，其业务 policy_tables 和 options 文本仍在；两 GUI arm 的 value 删除仍在之前逐项审计的范围内。

## 5. 最终联合发现：四条空输出，不是四次核验失败

四例实际请求均只含公开目标、投影状态、公开选项和旧行动标签集合，没有旧 O/B/claim、history 或 pending。审查者逐项确认实际消息文本与 context.json 相等、base64 图片与对应完整 chart.png 字节哈希相等。本版未调用 verifier 或 actor。

- pub001 误导图：notes 已称旧 TX 结论是最低值解释，却断言没有其他可由图面支持的结论。它没有交付 ME 竞争链；“覆盖充分”的文字也不能作为覆盖已证明的证据。
- pub001 正常图：返回零条，notes 仍支持 ME；在已有结论覆盖的情况下，零条本身不构成方法失败。
- b002：仍仅依印字 Edge 87% 排除额外解释，未提取图上 Firefox 柱更高的路径。这个遗漏与 V6 静态观察一致，但不是独立重复实验。
- pub013：notes 反称 KS 最高风险、IL 被色标否定，与该图浅色 High 的可见方向不一致。两个 C 已存在使其无需强造第三个，但 notes 的图面判断依然应标注错误；并保留上节输入删减限定。

没有手工把 notes 补成模型 chains，也没有将审查者看到的 b002 高度读取计入模型产出。

## 全轮归档与停止边界

独立读取最终 ledger 并按 events 计数：**89 次真实请求尝试、78 次浏览器操作，89 个 HTTP 200、零重试、零付费 API 请求**。最后阶段新增 4 次请求、0 次操作。它不是把前面的总账重新从零开始。

`RESULTS_SUMMARY.json` 记有 14 次真实业务提交，来自 pub001 的两个共享 checkpoint 上七个 GUI 开发分支，不是 14 个独立任务。误导图有一次全图核验后实际纠正（V5），其他已执行 GUI 版本仍保持错误；正常图各版保持 ME。不要把这些适应性分支合并成总体恢复率。两个静态样本以及最后四例候选诊断没有真实提交。

本地逐一对照六个阶段 `source_hashes.json` 与其 `runtime_source` 中的对应文件，**153 条快照哈希记录全部相符**。阶段请求/操作增量为：主四方案 30/40，全图追加 13/14，原静态迁移 12/0，契约版 12/12，隔离及静态续接 18/12，最后联合发现 4/0。此前 b002 的假设指向/返回指向不一致属于输出接口失败，契约版静态的换行哈希错误属于推理前工程中止，均不能算成“已运行核验而语义失败”。

下一步可据这份工件讨论输入契约及生成/核验职责边界；本轮到此停止，不补跑八方案、不制造正反答案、不再用剩余额度探索第九种版本。
