## 提示：没有发现任务答案硬编码

新提示未写实体名、数字答案、特定样本 ID 或固定印字/几何/图例优先规则。要求把不同编码分开读取、比较完整 O 条目、缺依据使用 unclear、具体反证才 refuted，属于针对已知失败类的通用改动。

不过提示变长、新增一次读取与核验职责说明同时改变，不能把未来变化单独归因于“独立读取”或某一句话。读取与核验仍为同一个模型，二者一致不是独立真值。必要支持条件严格化也可能增加 unclear；不能只凭 refuted 变少或模型放弃选项宣称能力改善。

原 O/B 中自带动作文字没有清洗，仍不是真正结论盲审。新的 READ 没有候选锚定，不代表后续 VERIFY 也没有锚定。

## 工程核对及最小补强

### 已有保护

模型与端点只能为既有 Qwen3.8-27B/127.0.0.1:8058；禁付费，单并发全局 fcntl 锁；共享 ledger 在发送前递增尝试；每次发送前检查 560 上限和截止时间；未知传输异常写 blocked 并停止；已完成 stage 按完整 payload 比对后复用；旧结构失败不质量重跑；版本限制 v1/v2/v3；同一 run 续跑核对源码哈希。

不存在通过另开 panel 自动归零 budget 的路径。确认完整或接口失败的结果进入 full 时复用，不重复计费。没有操控 GPU 或其他作业的代码。

### 建议 1：冻结不只绑定 prompt

初审时 FREEZE 只校验 version 与 prompt_sha256；同名 prompt 下若 run.py、schema.py、config.json 或 manifest.json 改动，仍可能创建新的 panel。虽然确认复用时有完整 hashes 对比，但未复用的全量单元仍可在改变后的 runtime 运行。

建议 FREEZE 一并绑定 source_hashes(version)，并对 confirm/full 检查整个集合；这不是增加语义门禁，只是让“冻结版本”包含输入与解码协议。应在确认开始前完成，不在结果出现后改写旧快照。

复核更新：run.py 已在非 dev 面板检查 `frozen['runtime_hashes'] == source_hashes(version)`；主代理记录为首次启动前修复。该项已处理。

### 建议 2：异常 JSON 也应先归档

Client.call 对 response.json() 的返回直接使用 body.get，然后才保存 response。若服务意外返回 JSON 数组/字符串，原响应未归档即抛错，外层会标 interface_failed。

建议先保存任何原始 body，再安全读取 object 类型的 usage/model；非 object 返回作为明确接口失败保留。不要为了修此问题增加真实探针；一个 Mock 返回数组即可覆盖。

### 建议 3：已归档 200 的 crash recovery 账本

若进程在 response_200 文件保存后、ledger 保存前退出，续跑能复用该响应，不会多发请求，这一点安全；但旧 event 可能仍为 sent_outcome_pending 且缺 usage。建议恢复时利用同一 folder/attempt 的原响应旁证完善 ledger 元数据并注明恢复，或最终明确账本待定且从响应单独计量。不能把实际响应已有用量遗漏为零。

### 对停止的限定

提前 preflight 失败发生在主要 try/finally 之外，summary 可能仍写 running；自动化接续应同时检查 PID/锁和日志，不能仅靠 summary 字面判断是否仍有作业。不存在授权停掉其他进程的推论。截止前发出的请求可在超时窗口内返回；截止规则应报告为“之后不发新请求”，不是保证全部输出已在该时刻结束。
