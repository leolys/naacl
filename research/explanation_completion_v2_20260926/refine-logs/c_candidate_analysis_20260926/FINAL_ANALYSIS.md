# C 生成职责：候选结论与核验结果分离（分析稿）

状态：proposed_not_implemented。2026-09-26。本轮只回应用户的提示分析请求，不修改运行代码，不追加实验或 API 调用。

## 问题锚点

生成器负责展开有实质差异、完整且可检验的 O–B–C 候选；反问补齐尚未表达的读法；后续核验器判断观察、规则适用性和推导是否成立。生成器不应先用“支持不足”取代具体 C，也不能为凑链数编造 O、循环定义 B 或随机写结论。

## 当前证据

现有 prompts.py 的 COMMON 将“缺少前提应报告缺口”放在所有阶段的 C 说明中；GENERATOR/SUPPLEMENT 模板把 claim 同时定义成具体结论或缺口记录，claim_kind 允许 undetermined，new_chains.relationship 允许 support_gap。因此仅删除一处自然语言仍留下用缺口代替候选的输出通道。原方法 §3.2 允许条件性假设先生成、后核验，同时曾允许解释缺口；本次建议是明确缺口的记录位置，不删去其存在的事实。

## 建议的最小修订

1. C 仅存候选读法的具体任务结论；规则及未核验假设明确写在 B/conditions。C 不是验证状态。
2. 生成器尽力给出连贯、可检验的解释，不需要先证明它正确。错误候选可以进入核验；这不是要求故意产生随机错误。
3. 原来的否定推导/全局最大完整性检查提醒放入 VERIFY，不放在 C 生成段落里诱导提前裁决。
4. 完整解释列表中的 claim 不再兼任 missing-premise record，undetermined 不再是 C/新链类别。确实未构成候选的事项复用 question_responses.unresolved；已有解释的补证/条件说明保留 refinement，但不计作新的 O–B–C。
5. 保留独立核验器的 O/B_applicability 三态及 conditional_inference 检查，不把“生成具体 C”混同“C 已确认”。现有真假/缺口核验不能取消。
6. 在预算内优先覆盖未表达的实质读法，不强制相反答案、固定多出一条、或重复已覆盖读法。

## 建议替换的 C 段落

C 是当前候选读法所主张的具体任务结论，而不是核验结果。根据本链记录的 O 和所采用的 B，明确写出这一读法认为哪个对象满足或不满足任务要求、存在什么比较或变化，以及由此支持或反对什么行动。B 中的解释假设在此作为本候选采用的读法，不要求在生成 C 之前已经得到独立证实。即使该读法可能错误、与其他候选冲突，或会被后续核验否定，也应表达其具体结论。不要用“无法确定”“支持不足”“需要进一步检查”等核验性说明代替 C。所有解释假设应明确写入 B 或 conditions，不得伪装成 O 中的可见事实，也不得把预期结论改写成 B 来循环支持它。不同链可以得到相同或不同结论；它们的价值在于解释依据存在实质差异，而不是必须给出相反答案。候选是否正确，交由后续核验环节判断。

## 异常与验证边界

若确实未形成可识别的读法，将未完成问题留在链列表外的现有问题处理记录，不制造一个只有“不确定”的 C 来充数。输出约束只要求候选完整、假设透明、解释与观察存在可描述联系；逻辑是否成立仍交给核验，不在程序里凭 Codex 判断删候选。

本轮不声称提示改动已经改善生成效果。未来若实现，应同时修改共享提示和生成/补齐 JSON 合同，保留旧记录与新旧口径，不直接重标旧结果。

## 审查后的取舍

采纳：C不能同时当候选结论和核验状态；输出格式须同步移除用gap充当new_chain的通道；放宽B预先证实要求的同时保持假设透明、反循环定义、实际观察来源。真正无链可形成时需要链外未完成记录；补齐阶段可直接复用已有unresolved出口，初始生成对应出口尚需未来实现。

不采纳将反问收窄成“只寻找另一条新链”：用户目标包括补齐已有解释，因此仍允许反问定位遗漏观察和条件并形成refinement。反问可以提出是否遗漏必要比较的问题，但不把问题自带的结论当核验结果。不必为此次分析重命名全部proposal_relation枚举；只要它表示候选立场而非核验结果，并继续从独立核验输入剥离即可。

论文中的“可记录解释缺口”将来若调整，应澄清为链外问题/细化记录，不直接改写用户原稿或否认原稿已有表述。本轮只保存分析记录；运行提示、代码、数据和实验结果均未改动。使用research-refine的锚点与一次审查，未启动广泛查新、评分循环、实验计划或付费验证。审查为同族暂定意见，不是效果证明。
