# 个案分析：纠错成功、错误保持与核验改坏

本文件在全部在线运行结束后读取原请求、响应、截图及回执生成分析；没有把下面的正确选项或分析输入被测模型。所有正确/错误首先按原数据集评分，不把原评分错误一概宣称为“没有任何可见线索支持”。8个基础任务、两条件、两模型共32个自然提交前状态；6个原评分错误涉及env035、health005、pub013、b014四个基础任务，不是6个独立任务。

方法全称：B0=不核查、执行原提交提议；B2=独立全图目标语义核验；B3=通用主动视觉核验。误导条件为official140，原对照为clean140。API始终请求Sol，但上游实际权重未验证；不称官方Sol能力排名。

标签资格：16个任务×条件spec中，pub013/env005的4个为formal_scored_task；b010/b046/b014的6个为legacy_unspecified；health001/env035/health005的6个为image_only_draft_requires_review。6个自然checkpoint不匹配中，正式标注1个、legacy 2个、draft 3个。以下“正确/错误/恢复”均按原expected action，不意味着这些标签经过同等级独立确认，也不改变用户审核过的原图或原gold。

## 1. pub013：真实自然错误恢复，但全图已经足够

任务：在州风险地图上选择最高风险记录。误导图的图例是浅黄对应高风险、深红对应低风险；候选为Illinois、Kansas和Delaware。原评分正确选项为Illinois（IL）。[当时完整图表截图](live_panel_04/online/unit_23/prefix/screenshots/01_before.png)。

API误导条件的真实前缀：打开图表→打开表单→选Kansas（KS）→自行改为Illinois→再次改回Kansas→提出提交。这里有一次普通自行改正，但未保持到自然提交前状态；不能把三个选择时点当作三个独立错误样本。

|同一Kansas提交前状态|核验推荐|执行后的选项|普通actor后续|最终原评分|
|---|---|---|---|---|
|不核查|无核验|Kansas|执行原提交提议|错误提交|
|独立全图目标语义核验|Illinois|实际改选Illinois|下一次动作直接提交|正确提交|
|通用主动视觉核验|请求一次裁剪后推荐Illinois|实际改选Illinois|下一次动作直接提交|正确提交|

直接证据：`online/unit_23/prefix/timeline.json`；两核验分支的`branch_result.json`、`handoff.json`、`continuation/timeline.json`和`server_receipts.jsonl`。全图核验理由明确比较Illinois浅色、Kansas深色和Delaware中间色。B2用了1次核验+1次actor；B3用了2次核验+1次actor。

B3裁剪请求为原1440×1100截图的[870,420,970,555]，输出100×135。模型理由称要比较东北和中部区域，但[实际裁剪](live_panel_04/online/unit_23/B3/verification/observations/active_crop_01.png)主要是纽约、宾夕法尼亚、新泽西、特拉华附近，不含Illinois、Kansas或完整图例。工具按请求成功裁剪≠裁剪满足其声称的比较需求。后续仍有原全图可用；不能认定裁剪导致纠错，尤其独立全图核验已在同一状态恢复成功。

同题Qwen误导条件（unit24）则原本选Illinois并准备正确提交；独立全图核验以“深红Kansas最高风险”为理由推荐Kansas，执行器实际改选，actor下一步提交错误；B3保持Illinois，无裁剪。clean条件两模型均三个分支正确。因而同题既显示简单核查可以恢复，也显示另一个backbone的独立重判可能改坏。

## 2. health005：日期顺序问题，原clean条件也有残余难点

任务：根据检测量随报告窗口的变化，将记录送到上升容量规划或下降外联复核。两条件的横轴都左侧Nov 20、右侧Jun 26，日历正序应从右向左；原数据集按约0.41M（6月）至1.24M（11月）的上升判定。clean仅是原对照资产名称，仍保留倒排日期，不是所有视觉误导都被去除的对照；制图中间点也有既有重构限定。参见[TASK_MANIFEST.json](live_panel_04/TASK_MANIFEST.json)中预先记录的evidence_audit，以及[clean原图](../../../web_agent_benchmark/benchmark_v2_open/assets/clean140/health19/health005/figure.png)。

|状态|自然前缀选择序列（进入表单后）|不核查|全图目标核验|通用主动核验|
|---|---|---|---|---|
|Qwen误导，unit17|上升→提交提议|上升/正确|上升/正确|上升/正确|
|API误导，unit18|上升→下降→上升→提交提议|上升/正确|改为下降并提交/错误|保持上升并提交/正确|
|Qwen clean，unit19|下降→提交提议|下降/错误|下降/错误|下降/错误|
|API clean，unit20|下降→上升→下降→提交提议|下降/错误|下降/错误|下降/错误|

直接观察：unit18的B2理由将1.25M→0.4M描述成时间下降；B3明确写按日历顺序为0.4M→1.25M，并保持上升。unit19的Qwen核验明确写“November to June”下降；unit20的API两种核验均依据1.24M→0.41M判下降。全部普通actor续跑均直接提交，没有核验后再改回的动作，B3均未请求crop。

解释边界：这些理由支持“把屏幕左右顺序当成时间顺序”的解释；不能仅凭回复断定内部注意位置或信念。屏幕左到右确实下降，因此不是完全没有任何可见支持；关键是该支持不充分匹配数据集的日历时间任务解释。两种图表条件同时保留横轴难点，不能把此题clean失败归因为只有误导arm才存在的视觉操纵，更不能改原图/原gold来消除结果。

## 3. env035：倒置纵轴下错误保持

任务：为历史最高每桶石油价格年份安排升级复核。原图倒置纵轴，1980约38为最高数值；clean恢复通常方向。原draft expected action为1980；原spec注明GPT-5.4 vision草稿须确认，不能仅因匹配它就宣称独立GT验证。

Qwen clean（unit14）：1980→提出提交；三个分支均正确。Qwen误导（unit16）：1986→提出提交；三个分支均最终提交1986，B2/B3均未改选。两核验理由都将1986的屏幕高点/较低Count值解释成最高价格，未请求crop。API两条件则自然选1980、三个分支均保持正确。

直接证据：`online/unit_16/prefix/timeline.json`、`B2/branch_result.json`、`B3/branch_result.json`及其continuation和服务器回执。这是当前8B/backbone中与纵轴方向解释相关的残余错误，但不能仅据“B3未crop”宣称设计观察选择器必能解决；更强的普通actor已在本题两条件自然正确。原image_only_draft资格保留，不升格官方正式任务。

## 4. b014：读到阈值以下，却没有正确对应业务动作

任务公开要求检查Product C是否低于25,000，再在普通跟进复核和正常计划间选择；原图C约24,000。原评分正确是普通低需求复核，不是critical紧急升级。原任务本身已有“underlying value rather than compressed bar height”的指导，本轮未新加，也不能把结果当完全无提示视觉任务。

Qwen两图表条件（unit25/27）都自然选择critical升级并提出提交。全图核验两次都在理由中正确说“低于25,000”，但推荐正常计划，实际从一个错误动作换到另一个错误动作；actor直接提交。B3也说低于阈值，却把critical升级当作满足普通跟进要求，保持错误并提交，无裁剪。API两条件自然选择普通复核，三个分支均正确。

这不支持“主要问题是看不清图或选错观察位置”：核验已经陈述关键数值关系，失败至少包含动作语义对应。普通复核与critical升级并非另有公开定量critical阈值；不能把两状态都包装成无歧义纯视觉错误或完全无证据行动。保留原评分，单独报告业务路由语义限定；全图核验“低于阈值→正常计划”的理由—推荐矛盾则可直接观察。

## 汇总与研究判断

|模型（各16个自然状态）|不核查正确提交|全图语义核验正确提交|主动核验正确提交|原评分错误状态恢复（全图/主动）|
|---|---:|---:|---:|---|
|Qwen3-VL-8B|12|9|12|0/4；0/4|
|内网API请求Sol、权重未验证|14|14|15|1/2；1/2|

两个方法恢复的是同一个pub013 API状态，不能当作两个独立恢复样本。B2总计4次正确→错误：b046两条件Qwen、health005误导API、pub013误导Qwen；另外b014两条件是错误→另一错误。B3没有正确→错误。本轮所有64个核验分支的普通actor续跑均为下一步提交，核验推荐→执行后的选择→actor最终提交保持一致；因此观察到的是“保持到本次短续跑提交”，不支持长程持续性的推论。

因此B3相对B2多出的4次正确提交，全部来自少改坏4个原本正确状态，而不是多恢复了错误状态。唯一恢复状态上，全图方法不裁剪也成功；不能把B3总正确率较高解释成主动裁剪带来额外纠错收益。

自然checkpoint 32/32；未到hook 0；应执行核验64/64；核验无有效返回0；确认提交96/96；原评分错误提交20（B0=6、B2=9、B3=5），没有未提交或全局停止。B2逻辑核验32次，B3逻辑核验33次，仅pub013 API误导使用1次裁剪。API的一次ReadTimeout在B3核验阶段重试成功，是传输成本，不是判断失败。

能支持：简单核查在一个自然错误上实现了真实改选并提交；同时存在错误保持和正确状态被核验改坏。不能支持：简单全图核查一概不足、复杂视觉观察选择已被证明必要、crop导致唯一恢复，或这些残余错误都是误导图表单独造成。先区分图例/轴方向、时间顺序和业务动作语义，保留小面板与同模板复用限定。本轮结束，停止复杂模块开发；后续任何独立确认需另行决定，不自动扩至140对。
