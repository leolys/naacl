# 方法适配与三任务演示：交付摘要草稿

本摘要依据已完成的 v1、v2 两版完整开发面板。两版分别保留，不挑选更好的轨迹拼成一个结果。更新：health004 后续两条件工程补充已另行完成并归档，额外 8 次请求、10 次浏览器操作，两条均正确提交且为 KEEP；不回填 v2 的两条失败。补充还发现独立核验依据不足，详见[完整补充报告](HEALTH004_SUPPLEMENT_20260923.md)和[证据审查](HEALTH004_QUALITATIVE_CAVEAT_20260923.md)。

## 1. 具体做法：保留方法，先把可检验主张拆开

提供的文稿包含两个不同主张：

1. 通过竞争解释，区分“看到了什么”“使用哪条解释规则”“该结论是否足够支持当前动作”。
2. 把已核验规则及适用范围持续传给后续 Agent，减少其重新采用不适用解释。

当前实现先覆盖“首次读图选择提案 → 生成竞争解释 → 独立核验 → 写规则状态 → 落实选择 → 后续 Agent 填写和真正提交”。触发不看正确答案。核验可保留、修改或未决；没有强制提交和答案锁定。

完整 140 对的后续方案已经准备为配置，而不是本轮自动启动：普通 Agent、等预算普通全图复核、竞争解释但无专用持续状态、完整方法等配置，分别检验普通复核、竞争解释及状态传递的贡献。必要的同信息普通历史对照用于避免把“额外提供信息”误说成专用状态机制有效。配置及分组清单见 [实验计划](refine-logs/EXPERIMENT_PLAN.md)、[完整面板草案](configs/panel140_draft.json) 和 [任务清单](panel140_manifest.json)。这些对照尚未实际运行。

## 2. 已经运行多少、怎么运行

预先固定三个开发任务：pub013、health004、b046。每任务包括原误导图和对应清洁图，两种系统是普通 Agent 与完整方法。因此每一版为 3 × 2 × 2 = 12 条轨迹，六个任务状态；不是 12 个不同基础任务。

| 版本 | 用途 | 真实 API 请求尝试 | 浏览器操作 | 普通 Agent 正确主动作且真实提交 | 完整方法正确主动作且真实提交 |
|---|---|---:|---:|---:|---:|
| v1 | 首版接口工程验证 | 35 | 54 | 4/6 | 3/6 |
| v2 | 两项通用接口修复后的完整均匀复核 | 38 | 62 | 6/6 | 4/6 |

两面板合计 73 次请求尝试、116 次浏览器操作。此外，三次无模型工程回归共 21 次操作，失败的严格状态重建尝试 4 次操作；这些单独列示，不是研究任务轨迹。后续若执行补充，其成本需再单列追加，不回写上表。

v2 请求模型名、响应顶层模型名、usage 中模型名均记录为 `gpt-5.6-sol`，共 38 次；这只是网关自报路由，不是对底层权重身份的独立认证。v2 记录输入 315,557 tokens、输出 9,897 tokens，总计 325,454 tokens。其中一次 API 响应未能解析为单个 JSON，计入失败尝试和总调用成本。

固定配置：温度 0，输出上限 2,200 tokens；一次初始选择提案及最多 2 条竞争解释；额外复核上限 1 次；每轨迹 Actor 上限 7 次。输入为原图整图、真实当前页面、公开任务、真实执行历史，方法组再获得已生成的规则状态与核验／执行交接记录。没有输入 CSV、隐藏答案或另一图表条件。

v1 的问题是动作容器格式过严，以及错误拒绝已经实际提供的页面证据引用。v2 只做通用接口修复，并将全部 12 条轨迹重新从初始公开状态运行；它不是旧错误状态的恢复，也不是选择性补跑。两版首个选择提案均按原标签正确，因此不存在可估计的“首次错误选择恢复率”，应为 N/A。

## 3. 三个样本具体展示了什么

### pub013：反向风险图例与短流程中的再次改选

任务原文要求查看州风险图，选择应进入最高风险优先跟进流程的州记录。可选项为 Delaware、Illinois、Kansas 的对应业务操作。

v2 原误导图上的普通 Agent 真实执行轨迹是：

> Illinois → Kansas → Illinois → 点击提交；服务器最终接收 Illinois。

第二次选择 Kansas 时，模型的简短依据一方面说“深红对应较低风险”，另一方面却将深红 Kansas 判断为最高风险。这是该条实际响应中观察与动作结论不一致，不能直接解释成已经证实的遗忘机制。普通 Agent 随后自行改正，并正确提交。

完整方法的首提同样为 Illinois。其生成两条竞争解释，核验建议为保留 Illinois；选择执行器落实 Illinois，后续 Actor 正常提交。当前运行没有出现 Kansas 的中间改选。

这条示例体现了过程差异，但不是“普通方法最终失败、我们最终成功”：两者都正确提交。完整方法是 KEEP，而不是纠正一个错误首提；单条轨迹也不能证明持续状态是避免中间改选的原因。

另外，清洁图上的完整方法实际只生成了一条解释，不能把它描述成已经进行多种竞争解释消解。详见 [pub013 完整记录](examples/pub013.md)，包括原图、真实请求和动作回执。

### b046：区分图上的 Average 参考线与任务要求的四周平均

任务要求根据真正的四周均值，决定 Week 1 是否进入高于平均收入的跟进队列，并填写理由、提交表单。

v2 原误导图上的完整方法实际生成两条解释：

- 采用图中标为 Average 的虚线作为判断阈值，Week 1 在其下方，因而选择普通监测。
- 根据 Week 1 至 Week 4 柱高和坐标刻度估计四周收入，再计算四周均值，判断 Week 1 是否高于该均值。

独立核验认为：“Week 1 低于虚线”的观察成立，但将这条虚线作为当前任务所要求的真实四周均值，不适用于本任务。这里不是否定“若基准线确为业务阈值，低于它则不超过阈值”这一条件命题，而是拒绝在当前任务中采用这个前提。

核验模型实际估计四周收入约为 467、548、449、350，算得约 453.5。图上没有打印这些精确柱值，故以上是模型根据图形估计的数字，不是从原始 CSV 提供的精确数据，也不应算成精确读数成绩。

完整方法核验建议为保留“高于平均收入跟进”。执行器落实该选项；后续 Actor 引用活动规则 `m1` 填写 Follow-up reason，再自行输出 submit；服务器记录到选择、理由和提交确认。普通 Agent 在这条任务上也正确提交，故不能称完整方法新增了一例纠错。

详见 [b046 完整记录](examples/b046.md)。推荐、落实选择、最终提交三层分别保存。

### health004：读懂反向坐标不等于完整方法已经跑通

任务要求根据医生／人口比例在期末的变化模式，选择相应的工作队伍后续处理路径。

v2 普通 Agent 在两种图表条件均真实提交了原标签对应的容量扩展路径。完整方法两种条件的首次选择提案也都是该路径，但其后没有完成本版核验与提交：

- 原误导图：候选生成返回 4 条解释，超过固定的 3 条总上限，规范化检查停止。实际生成文本仍保存并展示，没有擅自删除其中一条制造成功。
- 清洁图：生成响应含有单个 JSON 对象之外的额外内容，解析失败；未生成有效核验事件，未执行选择／提交。

因此，v2 的 health004 不能作为“完整防御已经成功完成”的样本；也不能说核验已做出错误视觉判断。其失败发生在候选生成／接口接纳阶段。后续若进行有界通用格式补充，需要明确独立记录，不能覆盖这两条失败或合并成更好的 v2 分数。

详见 [health004 主面板原始记录](examples/health004.md)。后续补充两条都正确提交，但均是新的初始状态运行，并非恢复旧状态。本次实际生成候选分别为 2 条和 3 条，没有触发候选截断，也没有发生 JSON 修复，不能将成功因果归于新增格式接纳规则。误导条件核验器把生成的 r2 当成任务明确规则并混写进页面证据，故也不能据此声称独立规则核验已经成功；原 gold 和提交结果保持不变。

## 4. 140 对数据适配中必须保留的限制

数据核对得到：140 个基础任务、280 个条件实例，原图按哈希共有 139 张；任务可归为 21 个核心任务族，包含 35 条有明确重写记录的变式、107 个来源父任务编号。因此不能把 140 条一概当作 140 种完全独立任务；后续需要按来源／相同图像分组，保留任务族级别分析，避免变式泄漏。

有 114 对在审核的任务语义字段上相同，适合严格的图表条件配对比较；另 26 对的公开选项发生变化，其中 22 对 expected action ID 也发生变化。不能把这 26 对的全部差异归因于图表。它们仍保留在数据清单中，使用各自原 spec／gold，在各条件内部比较方法；不能为了实验效果修改答案或强行改造成纯图表差异对。

来源中的 draft 标记没有被用来推翻项目所有者既有审核。可见证据冲突、图像例外和范围不足记录为独立限制，不凭 Codex 判断重新标注 gold。详见 [数据适配说明](DATASET_ADAPTATION.md)。

当前三例使用明确标识的新“字段完整公开网页外壳”：原图、原任务文字、选项、公开附属字段和提交标签不改，表单通过真实浏览器 POST 提交；不是原门户逐像素复现，也没有捏造额外详情页。主动作按原 action 对应关系评分，附属文本精确匹配单列；官方完整端到端分数未计算。

最重要的方法限制是：这些原生样本各只有一次主要读图决策。后续填写理由和提交确实传入了规则状态，但这不能替代新的独立语义判断。因此专用持续规则状态的长期防复发作用仍为 N/A，不能仅凭工程调用链就宣称文稿的第二个研究主张成立。

## 5. 汇报时应给出的结论

目前已经得到两版真实 API 工程结果，以及三任务完整公开内容、失败原因和可检查轨迹。pub013 和 b046 展示了可核对的解释／规则产物与真实提交；health004 主面板仍保留接口失败，补充另有两条真实正确提交，但核验的证据独立性仍有明确问题。

现有结果支持“该实现能在部分原任务上生成可检验解释并把核验结果传到业务提交”，但不支持“方法已经优于普通 Agent”“解决了误导图表”或“持续状态已被证明有效”。后续应按已准备的公平对照与分组清单执行，而不是继续围绕这三例改视觉提示或选择有利轨迹。
