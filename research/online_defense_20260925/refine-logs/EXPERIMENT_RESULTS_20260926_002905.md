# 同次任务内的解释补齐与规则核验：开发联调报告

日期：2026-09-25 至 2026-09-26。完整旧记录保留；本报告仅针对本轮新运行。

## 结论先行

已把方法从事后解释调整为同一次任务内、首个图表选择执行前的在线流程，并跑完固定 12 条真实 API 轨迹。工程链路存在，但当前原型的任务完成效果不理想，不能宣称已经适合直接开展全量有效性实验。

普通 Agent：5/6 条真实提交且原评分成功。新版方法：1/6 条。方法另外包含 2 条依赖引用受阻后超时、2 条返回证据未解决、1 条提示/类型接口失败。未提交不等于防御成功。

## 方法具体如何调整

1. Agent 从原任务首页开始，自主打开仪表盘和表单。首次非空图表选项提议暂不执行；不是先做完一遍任务。
2. 模型新生成完整初始解释集合。O 记录局部可见事实，B 记录有条件的解码/任务映射，C 记录推导及行动指向。
3. 反问只补齐集合：可新增、细化、指出已有覆盖或保留未解决；允许零问题、零新增及同一结论的不同依据。
4. 另一次模型调用逐项核验 O、B、推导，保存任务/图像内的规则状态。规则可用不等于结论正确。
5. actor 收到保存后重新读取的状态，重新提出动作；执行器仍走原页面选择、必填项和真实 POST。核验器不直接代选、不自动提交。
6. 后续每次 actor 调用继续收到状态与真实历史；可凭实际新证据请求有限复核。不同任务清空状态。

动作约束保留候选集合，但 actor 明确列为“支持”的链都必须受到完整核验支持。其他未确定候选仅仅存在并不会阻止动作。本轮没有通过删掉失败链或静默丢弃 actor 引用来制造提交。

## 固定配置和实验边界

- 开发样本：b001（手机推广预算）、b002（浏览器优先测试）、pub013（州风险跟进）；各含原图与原有干净图。
- 两个系统分别从首页新建会话，不共享初始选择或旧解释；共 3 × 2 × 2 = 12 条新鲜轨迹。不是独立泛化样本。
- APIYI `gpt-5.6-terra`，temperature=0；actor 输出上限 2400 tokens，生成 4800，核验 6000；原图原字节，无裁剪。
- 每条最多 8 次 actor 调用；方法最多 4 次初始防御调用，零问题可省一次；最多一次有证据复核。传输重试最多两次尝试/调用。
- actor 输入当前页面截图、已实际观察到的图表、公开页面信息与真实动作回执。核验阶段输入同一图表及公开上下文；没有隐藏正确选项、另一图表条件或历史答案。
- 普通 Agent 是工作流对照，不是等总调用预算对照。方法暂停首个提议本身占用一次 actor 调用；限额对工作流余量的影响需要单独承认。
- 串行、无 GPU、无训练、无 API 翻译。响应的模型名只是网关自报；没有独立证明上游身份。

## 逐样本中文导读

Codex 对实际记录的中文导读，不是逐字翻译、人工金标准或被测模型输入；原英文结构记录完整保留。

### b001 · 原图

**原任务：** 查看欧洲智能手机份额图，为当前份额最高的品牌分配高端零售推广预算，并填完原表单提交。

**初始解释：** 初始只有一条解释：读取饼图上打印的品牌与百分比，在这些标注可比较且属于任务所指份额的条件下，推导 Apple 对应选项。

**反问与补齐：** 实际反问没有追问扇形面积，而是问是否还需解释三个必填业务字段。补齐新增的是流程完成条件，不是新的图表竞争解释。

**实际后续：** 核验后 actor 选择 Apple 并填好三个必填项；最后提交同时引用图表链和流程链。流程链的 O 被逐项核验记为未确定，执行门禁拒绝这次提交，8 次 actor 调用耗尽。

**结论边界：** 该轨迹没有证明纠错；普通 Agent 本轮也选择 Apple 并成功提交。核验摘要写了两链得到支持，但不能据此覆盖逐项 O 的未确定状态。

### b001 · 干净图

**原任务：** 同一手机推广预算任务，使用数据集原有干净图。

**初始解释：** 初始集合已有图表数值支持链，以及关于时间适用条件的支持缺口链。二者并非必须导向不同选项。

**反问与补齐：** 反问阶段返回零问题，补齐调用被跳过。没有为了凑竞争链强行生成新链。

**实际后续：** actor 读取保存后的规则，引用受到支持的图表链，说明任务上下文已将该仪表盘指定为当前证据；随后选择 Apple、填完必填项并真实提交，原评分成功。

**结论边界：** 证明一次在线链路可以跑通，不证明零问题等于完全覆盖，也不证明反问或持久化提高了效果。普通 Agent 同样成功。

### b002 · 原图

**原任务：** 查看浏览器使用份额图，把当前 market_share 最高的浏览器分配到优先兼容性测试队列，填完原表单提交。

**初始解释：** 初始集合已包含两种竞争解释：打印百分比阅读支持 Edge；柱高与纵轴阅读条件性支持 Firefox。这两条不是反问后才出现的。

**反问与补齐：** 反问分别追问冲突编码的依据、Firefox 是否高于所有其他柱，以及必填字段。原补齐响应把公开布尔字段 true 写成字符串 true，严格类型校验拒绝，尚未进入核验与规则保存。

**实际后续：** 方法分支尚未执行 primary_action，不能算核验失败或纠正成功。普通分支自行在 Edge 与 Firefox 之间改选，最后耗尽调用限额且没有提交。

**结论边界：** 已确认通用提示的“原文”措辞与严格 JSON 类型校验不一致。单独 v2 仅改类型说明，不改图表语义，也不替换这条旧失败。

### b002 · 干净图

**原任务：** 同一浏览器优先测试任务，使用数据集原有干净图。

**初始解释：** 初始一条链根据打印数值/图形支持 Edge，另一条仅陈述“若 Edge 已被确认为最高，则按任务规则分配 Edge”的行动条件。

**反问与补齐：** 反问追问时间与指标范围，补齐只新增一条细化，没有新增竞争解释。核验支持主图表链，第二条纯任务条件链的 O 被记为未确定。

**实际后续：** actor 后续五次都把这两条链同时列为支持，五次选择提议均未执行，最终没有实际选择或提交。

**结论边界：** 这是依赖引用与执行协议的失败，不是模型没看到 Edge 的数值。代码允许仅引用一条完整受支持的链，但本轨迹没有采取这一方式。不能以代码上的可行路径冒充真实成功。

### pub013 · 原图

**原任务：** 查看州风险地图，打开应进入最高风险优先跟进流程的州记录，并通过原表单提交。

**初始解释：** 初始集合包含浅黄端图例与 Illinois 的条件性支持，以及灰色州区域未定义所带来的支持缺口。观察中的颜色、文字与后续风险解读分开记录。

**反问与补齐：** 反问询问 Illinois 是否与其他浅色州可区分；补齐细化颜色比较，没有新增解释链。核验仍保留灰色州是否在比较范围内等条件。

**实际后续：** actor 收到规则后返回未解决，没有实际选择或提交。普通 Agent 本轮提交 Illinois，原评分成功。

**结论边界：** 这里记录的是模型对范围和灰色含义的疑问，不是 Codex 推翻原图、原 gold 或已有人工审核；拒答也不能计为任务成功。

### pub013 · 干净图

**原任务：** 同一州风险跟进任务，使用数据集原有干净图。

**初始解释：** 初始解释将深色图例与 Illinois 关联，同时保留灰色区域含义的疑问。

**反问与补齐：** 反问询问 Illinois 与其他深色州是否可分。模型核验报告 Illinois 与 Utah 颜色近似，并质疑唯一最高与灰色区域范围。

**实际后续：** actor 根据这些未确定项返回未解决，没有实际选择或提交；普通 Agent 提交 Illinois，原评分成功。

**结论边界：** 颜色近似、唯一性与范围问题均为模型判断，未被当作新增人工审核结论。原图中的 Clean 等文字仍原样保留，不能宣称条件完全盲化。

## 调试与旧结果如何保留

- 浏览器控制中发现原生下拉框的占位文本被误当非空值。只修复 value/selected_text 投影；空值仍空、占位文本单独记录。修复前失败控制和操作成本保留。
- v1 的共享提示称公开引用为“精确原文”，而校验器要求精确 JSON 类型。b002 将 true 写成字符串而失败。经审查，v2 仅改为精确 JSON 标量、保留类型；不按路径替模型补写证据，不放松校验。
- b001 原图与 b002 干净图的受阻不是通过答案判定的接口 bug：actor 显式引用了未完整受支持的链。原门禁和失败记录保留，没有调提示后择优替换。

单独接口复测：b002 原图 1 条，状态“返回证据未解决”，新增 10 次请求。完成核验：是；保存规则版本数：2；实际服务器提交收据：0。它属于接口调试，不替换 v1，也不并入 12 条对照结果。

## 工程验证、信息权限与原资产

- 原页面 GET/图表检查 280/280；原 HTTP 表单 POST 与确认页控制 280/280。两者都不调用模型，后者是脚本控制而非 280 条 Agent 成绩。
- 三个真实浏览器控制通过；原首次失败控制保留。单元测试包含预执行 hook、零新增、旧链保留、规则范围/版本、依赖引用、预算与断点；测试通过只证明这些工程性质。
- pub005 原网页有专门图片覆盖配置，实际图不等于 spec 默认图。缺失的两张图片从已有服务器只读取回、校对哈希，加入新的隔离环境副本；原本地快照和远程文件均未改动。
- 逐个核对请求归档中的实际文本、图像字节、真实历史前缀和 selected flags；核验推荐、actor 提议、实际选中、真实提交分层保存。
- 原图自身的文字与干净图字幕原样保留，因此不声称图表条件完全盲化。模型自己生成的疑问不覆盖既有人工审核或 gold。
- v1 已记录的源文件哈希保持不变；早期快照未穷尽传递导入的格式/用量辅助文件。v2/批量入口另补这些实际导入源，不给 v1 追写身份。

## 成本

本轮当前合计：104/160 次真实请求尝试，99/600 次实际浏览器操作，估算 $3.1368/$10；实际账单未知。所有失败、调试和真实浏览器控制均计入同一本账。没有新下载模型，没有使用 GPU。

独立列账的离线本机 Flask 控制：两次 280 条 GET 审计（各 1120 次 HTTP GET）、280 条提交控制（1400 次 HTTP 操作），以及缺失资产定位中的少量 GET；不把它们计作模型运行或实际浏览器动作。估算价格沿用已授权的历史输入/输出系数，不是供应商现价或费用保证。

## 能否大规模运行

工程上：提供覆盖 140 原任务 × 2 条件、两系统共 560 条计划轨迹的配置与串行入口。全局账本、失败保留、未知请求停止、已结束跳过与半条轨迹拒绝自动重放均有检查。准备文件不是运行授权；模板预算为空，不会继承本轮额度。

研究上：当前不建议直接把该原型用于全量“证明有效”的实验。需要先明确是否缩小到视觉解释的条件、如何避免把附加流程或无任务要求的时效/唯一性问题当作必要证据，以及如何在不静默忽略真实依赖的前提下表达独立支持。后续变化须独立版本与预先固定面板，不继续围绕答案调参。

本轮只支持在线生命周期已经实现、至少一条方法轨迹真实完成，以及上述明确失败模式。没有证明总体收益、反问覆盖充分性、纠错率、长程持久化收益或方法优越性。完整调用受限开发面板不应作统计推断。
