# 候选解释链生成修正（v3）

本目录与旧 v1/v2 并存，不覆盖旧结果。目标是补齐可检验的解释，不是强迫冲突、增加链数或证明纠错成功。

## 主要改动

- 提示要求初次生成与反问补充均输出具体 C；不再设置 `claim_kind` 分类，也不再允许 `support_gap` 作为新链关系。该要求不是对模型行为的保证。
- C 可以是肯定、否定、比较或行动结论。`option_label=null` 表示没有明确支持某个选项，不等于 C 不确定。
- 未验证的解释假设明确写在 B/conditions；O 仍须来自图面可见观察，不能为补链虚构观察或任务事实。
- 初始生成无法形成完整候选的问题放入 `unresolved_questions`，与解释链分开；后续问题通过 `question_responses` 记录是否补链、细化、已有覆盖或未解决。
- 后续核验保留 O 与 B 适用性的“不确定”，并独立检查条件推导。核验不改写 C；持久规则状态不是业务行动授权。
- 代码的结构校验只检查字段、引用和分工接口，不能证明自然语言 C 真的具体、正确、无循环或覆盖充分。真实输出仍需人审。

## 中文提示核心

> C 是当前读法所主张的具体任务结论，不是核验结果。按记录的 O 和采用的 B 清楚写出结论；B 的解读假设无需先被独立证实。不要用“无法确定”“证据不足”代替 C。形成候选的真实困难单列为链外问题。不同解释可以得到相同或不同结论，不必制造相反答案。

> 核验器再分别检查：观察是否支持、解释规则是否适用于当前图、在所列前提下结论能否成立。不能推出命题不代表推出否定；否定某候选是最大不代表已经找到全局最大。检查结论不得反写或覆盖原 C。

完整实际英文提示保存于 `prompts.py`，每次运行另存 `prompt_templates.json` 和完整请求。中文是阅读辅助，不是另一次模型输入。
