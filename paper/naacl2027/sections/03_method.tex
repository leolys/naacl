\ours{} rests on one object: the interpretation rule
$B$ that connects visual observation to task judgment.
Competing explanation chains make these rules explicit
and test them; persistent state organizes their revision
evidence, current validity, and applicability scope, so
that they participate in later interaction.
This section develops the two mechanisms in turn after
fixing the task setting.

\subsection{Task Modeling and Overall Framework}
\label{sec:method:setting}

Consider an agent executing a task $q$: at step $t$ it
receives an observation $o_t$ and, given history $H_t$,
proposes $\widetilde{a}_t$. When the proposal depends
on chart understanding, let $I_t$ denote the complete
chart observation relevant to the current judgment---or
the chart observation actually obtained earlier in the
task when the chart has left the current page. We
express a chart-driven interpretation as
\begin{equation}\label{eq:o-b-c}
O \land B \Rightarrow C_q(a),
\end{equation}
where $O$ is an observation in the chart, $B$ is the
interpretation rule required to convert the observation
into task semantics, and $C_q(a)$ is the proposition
that the action, or high-level choice, $a$ meets the
requirements of task $q$.
The representation separates a visible phenomenon from
the condition under which it is interpretable: a curve
moving upward, jointly with the rule that higher
position means larger value in the current axis,
supports the conclusion that the interval grows and the
action is admissible, while a mismatch against verified
numeric relations refutes precisely that rule's
applicability.
$O$ and $B$ may carry multiple items in structured
natural language covering entity binding, numeric
relations, encoding direction, time range, and
comparison conditions; explicitly computable relations
are checked with program assistance, and remaining
semantic judgments are verified jointly with the public
task requirements.

The method maintains a within-task rule state $M_t^B$
and, for chart-dependent judgments, runs the process
\emph{current interpretation $\rightarrow$
competing-explanation generation $\rightarrow$ in-chart
applicability verification $\rightarrow$ rule-state
update $\rightarrow$ action re-derivation}; later steps
read the applicable rules from the current context and
restart competing verification only when a relevant
judgment is first formed, when new evidence conflicts
with an existing rule, or when a rule's applicability
conditions are in question.
Local verification decides acceptance or revision;
within-task maintenance decides where a rule remains
effective.
The model's parameters stay frozen; the rule state
evolves only with observations and verification results
actually obtained.

\subsection{Competing Explanation Chains}
\label{sec:method:chains}

\subsubsection{Making the Current Explanation
Explicit}
When the agent proposes a chart-dependent choice
$\widetilde{a}_t$, the interpretation module forms, from
the complete chart, the public task, the admissible
history, and the current rule state,
\begin{equation}\label{eq:pi0}
\pi_0 = \langle O_0, B_0, p_0\rangle,
\qquad
p_0 = C_q(\widetilde{a}_t),
\end{equation}
stating which phenomena the chart is claimed to
contain, which rules carry the observation to the
conclusion, and which evidence those rules lack;
unsupported choices record an interpretation gap
directly.
``The color is darker'' stands as an observation, while
``the risk is higher'' stands only under a color-to-risk
mapping: explicit chains turn such omitted conditions
into objects for verification.

\subsubsection{Counter-Questions and Competing
Explanations}
The competing module poses three connected questions:
whether the current observation suffices for the
conclusion, which interpretation rules the inference
depends on, and whether the same chart admits another
evidence-based explanation under which the conclusion
fails or the action holds on different grounds.
From these questions the module generates a bounded
candidate set
\begin{equation}\label{eq:pis}
\Pi_t = \{\pi_0, \ldots, \pi_K\},
\qquad
\pi_i = \langle O_i, B_i, p_i\rangle,
\end{equation}
whose conclusions may support the
current action, refute it, or support a different
judgment; all candidates refer to the same complete
chart.
A competing chain is meaningful only if it differs
substantially in observation correspondence,
interpretation rule, applicability condition, or
derivation scope: two chains that both accept ``the
curve rises'' but adopt forward and reversed value
mappings disagree precisely on the applicability of
$B$.
A reversed interpretation enters as a conditional
hypothesis, unverified until the chart's scales support
it; the module may return insufficient support and need
not produce an opposing conclusion for every task.

\subsubsection{Normalization and Shared Rules}
Generated chains are normalized over observation, rule,
applicability scope, conclusion, and evidence
dependence; paraphrases are merged, a rule used in
several chains shares one verification state, and
different entities or comparison relations keep
separate evidence.
Unlike self-consistency, which aggregates answers over
reasoning paths \citep{wang2022selfconsistency}, the
object here is the rule each path depends on: repeated
generations of the same rule add no evidential weight,
and a new explanation matters only through different
evidence or a new applicability problem.
In the deployed pipeline the candidate set of a
verification node is the frozen per-task pool of one to
three pre-generated $O/B$ records (275 records across
the panel), so the chain budget of
Eq.~(\ref{eq:pis}) is instantiated as $K$ equal to the
pool size and diversity is a property of pool
construction---candidate rules differ in object,
condition, or scope by design; the online arm
re-derives chains at runtime under the same budget.
This multi-candidate structure relates to multiagent
debate \citep{du2023improving,
liang2024encouraging} and to single-path self-refinement
\citep{madaan2023selfrefine}, but the competitors
disagree only over the interpretive bases of one
rendered chart, and the adjudicator is an applicability
test against that chart rather than a vote or an
LLM-judged winner.

\subsection{In-Chart Applicability Verification}
\label{sec:method:verify}

Verification first extracts the disputes that genuinely
affect conclusions among the candidates, concentrating
on the disputed mapping when chains agree on the
observation, and on observation binding before rule
applicability when the dispute concerns entity--value
correspondence.
For each chain the module outputs
\begin{equation}\label{eq:vi}
V_i =
\bigl(\,
v_i^{O},\,
v_i^{B},\,
v_i^{\Rightarrow},\,
E_i
\bigr),
\end{equation}
where each verification status takes the values
support, refute, or undetermined, and $E_i$ records the
in-chart evidence.
Observation $O_i$ is checked for presence in the chart
and for entity, value, time, and unit binding; rule
$B_i$ for support by the current chart and satisfaction
of its applicability conditions; the derivation
$O_i\land B_i\Rightarrow p_i$ for sufficiency of the
confirmed premises, including candidate coverage, range,
and task conditions.
Verification always proceeds against the complete chart,
and the evidence record contains the observation
identifier, the content read, and which rule the content
supports or refutes.
The deployed checklist operationalizes the three
statuses: for $O$, located support or a genuine
contradiction, with no inserted quantifiers or causal
claims; for $B$, explicit necessary-condition tests
against public facts, including whether the known
labeled references would have the relations a proposed
decoding predicts, and an explicit order comparison
before any common scale is endorsed; for the derivation,
coverage, range, and task-scope conditions as confirmed
premises.
Verification takes the normalized dispute propositions
as input; the source role or repetition count of a
candidate is never a credibility signal, and
observations and interpretive conditions are confirmed
before conclusions, so a preferred answer cannot
justify a rule retroactively.


For rules incompatible over the same objects and scope,
the method checks which in-chart information
discriminates them: disputes with unresolved evidence
stay open, and rules applying to different axes,
series, or ranges have their applicability conditions
split rather than forced to one choice.
Verification may support a replacement rule or only
negate the original---that bar height and visible value
ordering disagree does not entail ``shorter means
larger,'' and the sound revision may be that bar height
does not directly support quantity ordering.
Rule revision therefore includes replacing a mapping
and disqualifying an inference route.

\subsection{Rule Revision and Persistent State Update}
\label{sec:method:state}

Each interpretation rule is maintained as a record
\begin{equation}\label{eq:m}
m_i = \langle
\mathrm{id}_i,\,
B_i,\,
\sigma_i,\,
s_i,\,
E_i,\,
\Delta_i,\,
v_i
\rangle,
\end{equation}
with $\mathrm{id}_i$ for later reference, $B_i$ the
interpretation rule, $\sigma_i$ its applicability
scope over chart objects, encoding components, and
semantic conditions, $s_i \in \{$pending, active,
disputed, revoked$\}$, $E_i$ the evidence supporting or
refuting it, $\Delta_i$ linking original rule, revised
rule, and the reason for the change, and $v_i$ the
revision version.
The state stores how the current chart is to be read
and on what evidence; object choices, answers, and
click actions are produced by the task reasoning itself
and recorded in the execution history.
A rule's scope binds by the conditions under which it
holds---a position--value mapping to the numeric axis
and series concerned, a color reading to the current
legend and metric, an overall-trend rule to temporal
order and comparison range; page changes unrelated to
the task goal do not invalidate a rule by themselves.

Verification produces rule-revision proposals
$\Delta_t^B$, applied as $M_{t+1}^B = U(M_t^B,
\Delta_t^B)$: a supported rule with an unevidenced
proposal is kept and the proposal retained as pending; a
refuted rule with a supported replacement activates the
replacement in the affected scope; a refuted rule
without a settled replacement is revoked and the
interpretation gap recorded; effective conflicts enter
disputed status while verification continues within
budget; and rules applying to different objects or
scopes are stored separately rather than overwritten
globally.
The ``active'' status expresses the judgment under the
evidence at hand; new effective evidence can change it,
or show that an earlier verification was itself
mistaken.
After revocation, content, scope, and reason remain in
the revision history; a reappearing rule must answer
the recorded refutation or supply evidence that changes
the applicability judgment---repetition, later position,
or a more confident phrasing forms no new ground by
itself.
A revision record answers why the rule had to change,
what interpretation is adopted now, and under which
conditions it applies (Appendix~\ref{app:example}
illustrates).

An invalidated rule does not by itself condemn the
current action, since
$\lnot B_0 \not\Rightarrow \lnot C_q(a_0)$: after
updating $B$, the method re-examines judgments that
depended on it, retaining those other effective
interpretations still support, so the admissible
outcomes are a rule change with the action retained (a
wrong reason for a right choice) or rule and action
changing together; judgments already recorded are
marked basis-changed for later re-confirmation, the
interaction history stays intact, and the currently
effective rules are organized by a separate read
interface.

\subsection{Reading and Using Rules over Continued
Execution}
\label{sec:method:read}

Let the interpretation context $c_t$ collect the
relevant chart objects, encoding components, metrics,
and task scope; the state reader returns
$\mathcal{R}_t = \operatorname{Read}(M_t^B, c_t)$,
whose directly usable part is
\begin{equation}\label{eq:read}
\mathcal{R}_t^{\mathrm{active}}
=
\{\, m_i \in M_t^B :
s_i = \mathrm{active}
\land
\operatorname{Match}(\sigma_i, c_t) = \mathrm{true}
\,\}.
\end{equation}
$\operatorname{Match}(\sigma_i, c_t)$ evaluates the
rule's object, encoding component, metric, and time
window against $c_t$ and returns applicable,
non-applicable, or undetermined; an undetermined match
triggers verification of the corresponding condition
rather than assuming a stored rule covers the new
chart.
Disputed rules never enter
$\mathcal{R}^{\mathrm{active}}_t$; they surface only
as re-verification evidence in the read result, which
also carries disputes and revocation records, so the
agent separates interpretations still in force from
ones that lost support, and revoked content never
derives facts.
When a chart has left the viewport, the reader keeps
supplying applicable rules through the chart references
established within the task, and new chart objects or
encoding changes are bound and verified afresh.

The base agent produces its next proposal from the
current observation, history, and rule view,
\begin{equation}\label{eq:policy}
(\widetilde{a}_t, \widetilde{\pi}_t)
=
\mathcal{F}_\theta
\bigl(q, o_t, H_t, \mathcal{R}_t\bigr),
\end{equation}
where $\widetilde{\pi}_t$ is a short interpretation
record of the present judgment.
Rules about the same chart can remain valid while the
correct action changes with task conditions, so
interpretation evidence is reused across steps while
actions are re-derived from the current observation and
the public task.
A proposal depending on a revoked rule is returned the
revision evidence and required to re-derive; a proposal
bringing evidence sufficient to challenge an active
rule re-enters competing verification---restraining old
conventions from regaining force without grounds while
preserving a channel for correcting earlier
verification mistakes.
Ordinary actions follow the original interface; the
persistent state acts through later contextual reads,
with complete competing verification only when a
trigger holds.

Three observable entry points start verification: the
first chart-dependent judgment of a task (which
establishes the rule state), an interpretation conflict
(a later proposal uses a rule inconsistent with the
effective state, or an existing rule is challenged with
in-chart evidence), and an applicability change (the
chart, its encoding, the series binding, or the task
scope changes in ways that can affect interpretation).
Entry points depend on actual observations, task
context, and action proposals; task correctness and
hidden scoring never participate in triggering.

After a rule update, the agent re-judges the action and
records \emph{Keep} (the choice remains supported by an
effective interpretation and the task conditions),
\emph{Revise} (relevant evidence negates the choice and
an alternative gains the support the task requires), or
\emph{Unresolved} (an interpretive dispute that could
still change the judgment persists, or necessary
evidence is missing).
Showing that a candidate exceeds the current choice
refutes ``the current choice is highest'' while
confirming the replacement still requires the
comparison the public task demands; such checks belong
to task-semantic verification, not one fixed formula.
Unresolved status continues whole-chart verification
within the remaining budget, and an exhausted budget
records the unfinished reason explicitly.
Verification suggestions, actual choice revisions, and
final submissions are recorded separately, and only
operations carried out by the executor constitute action
outcomes.

\subsection{Full Algorithm and Integration}
\label{sec:method:algorithm}

Algorithm~\ref{alg:cers}
(Appendix~\ref{app:algorithm}) summarizes one execution
of \ours{} under budgets $K$ and $L$ for one
verification node.
The framework enters an existing agent at three
points---the observation entrance establishes chart
references, the pre-execution point performs
verification and rule revision, and the later-reasoning
entrance reads the currently applicable rules; planning,
execution, and review modules share the rule state
within one task, while action capabilities and the
environment interface follow the original system.
Explanation generation and verification can use
different calls of the same frozen model, with
deterministic code for record keeping, merges, version
updates, scope retrieval, and explicitly computable
checks; budgets and triggers are fixed before a run and
charged to the method's cost.
The rule state is isolated per task: the runtime sees
only the chart and interaction information the task
permits, the paired chart, hidden answers, and scoring
feedback stay on the evaluation side, and records are
stored separately so later analysis can trace how
evidence changed and whether operations followed.
